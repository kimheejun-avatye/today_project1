# 최종 회원가입 계획서

> 최신 구현 상태와 갱신한 계획서는 [project1/최종 회원가입 계획서](project1/최종%20회원가입%20계획서.md)에서 관리한다. 아래는 기존 논의 기록이다. 숫자 이미지 캡차·Google 추가 정보·개발용 개인정보 동의·만료 기록 정리 및 PostgreSQL 가입 검증을 2026-10-13에 추가했다.

작성 기준: 2026-10-13 대화 및 현재 구현 코드

이 문서는 기존 `회원가입-설계-계획서.md`의 회원가입 부분을 최신 입력 항목과 화면 흐름에 맞춰 다시 정리한 문서다. 로그인·일기 설계는 기존 문서에서 관리한다. **확정한 정책과 실제 구현 상태를 구분하며, 최종 계획서라는 이름이 모든 외부 연동의 완료를 뜻하지는 않는다.**

## 1. 목적과 범위

TypeScript 화면과 Python API 서버로 이메일 가입과 Google 가입을 제공한다. 단기 학습 프로젝트이므로 추가 시스템을 최소화하면서, 선택한 기술의 이점과 부담을 설명할 수 있는 구조로 만든다.

- 일반 가입: 서비스가 비밀번호를 관리하고 이메일 인증 후 회원을 생성한다.
- Google 가입: Google 인증 결과를 서버가 검증한다. Google 비밀번호를 받지 않는다.
- 이메일은 로그인 ID다. 별도의 사용자 ID 입력란을 추가하기로 결정하지 않았다.
- 이름, 생년월일, 전화번호 입력은 본인 확인이나 실명·연령·전화번호 소유 인증이 아니다.

## 2. 회원가입 화면과 수집 정보

가입 화면을 열면 모든 일반 가입 입력란을 즉시 보여주고 입력할 수 있게 한다. 이메일 인증 전에도 이름 등을 입력할 수 있지만, **가입 완료는 이메일 인증 후에만 가능하다.**

현재 화면 순서:

1. 이름
2. 생년월일
3. 닉네임
4. 전화번호
5. 자동 가입 방지 — 독립된 영역
6. 이메일 인증 — 이메일과 이메일 인증번호를 담은 독립된 영역
7. 비밀번호
8. 비밀번호 확인
9. 가입 완료

| 항목 | 용도 및 입력 기준 | 저장 방식 |
|---|---|---|
| 이름 | 필수, 공백만 입력 불가, 최대 80자 | 회원 테이블 |
| 생년월일 | 필수, 실제 존재하는 날짜, 미래 날짜 불가 | `YYYY-MM-DD` 문자열 |
| 닉네임 | 필수, 공백만 입력 불가, 최대 40자 | 회원 테이블. 중복 금지는 현재 정책에 없음 |
| 전화번호 | 필수, 현재 서버 형식 검사 적용. 문자 인증 없음 | 회원 테이블 |
| 이메일 | 필수, 로그인 ID 겸 이메일 인증 대상 | 소문자·앞뒤 공백 정리 후 저장, DB 고유 제약 |
| 이메일 인증번호 | 이메일을 사용할 수 있는지 확인 | 임시 인증 테이블에 검증값 저장 |
| 비밀번호 | 일반 가입 필수, 12~128자 | Argon2id 해시만 저장 |
| 비밀번호 확인 | 오타 방지, 첫 비밀번호와 같아야 제출 가능 | 화면에서 비교하며 별도 저장·전송하지 않음 |
| 캡차 응답 | 자동 가입 방지 확인 | 회원 프로필 항목으로 저장하지 않음 |

비밀번호 확인란은 입력 중 일치 여부를 안내하고, 불일치하면 가입 요청을 보내지 않는다. 최소 가입 연령과 별도 연령 인증은 정하지 않았다.

### 이메일 중복 처리

별도 중복 검사 버튼은 제공하지 않는다. 가입된 이메일로 가입 인증번호를 요청하면 서버가 ‘이미 가입된 이메일입니다’라고 응답하고 화면에 안내한다. 이메일 중복 가입은 서버 검사와 DB 고유 제약으로 막는다.

## 3. 자동 가입 방지와 이메일 인증의 구분

| 구분 | 자동 가입 방지 | 이메일 인증 |
|---|---|---|
| 목적 | 자동 프로그램의 반복 가입·발송 남용을 줄임 | 해당 이메일에 접근할 수 있는지 확인 |
| 사용자 입력 | 연결 예정인 이미지 캡차의 숫자 | 이메일로 전달받은 인증번호 |
| 검증 주체 | 서버 또는 캡차 서비스 결과를 검증하는 서버 | 우리 API 서버 |
| 관계 | 이메일 인증 성공을 대신하지 않음 | 캡차 통과를 대신하지 않음 |
| 현재 상태 | 서비스 미연결 안내 표시 | 개발용 인증 흐름 구현, 실제 메일은 SMTP 설정 필요 |

화면에는 두 영역의 제목과 설명을 따로 제공한다. 이메일 인증 성공 시 **‘이메일 인증되었습니다’**를 표시한다. 캡차가 연결되지 않은 상태를 ‘로봇이 아닙니다’ 또는 인증 성공으로 표시하지 않는다.

### 캡차 연결 계획과 현재 차이

- 사용자는 이미지의 숫자를 보고 입력하는 캡차를 연결할 의사를 밝혔다.
- 이미지 캡차 제공자, 이미지 갱신·만료·실패 제한과 접근성 대안은 아직 확정하지 않았다.
- 현재 코드에는 Turnstile 연동 틀이 있으나, 이것이 요청한 숫자 이미지 캡차 구현을 뜻하지는 않는다.
- 운영에서는 캡차 검증 후 인증 메일 발송을 허용한다. 개발 환경에서는 키가 없으면 검사를 생략하고 이를 안내한다.
- UI 영역을 분리했다고 캡차를 선택 사항으로 바꾸거나 서버의 발송 전 검증을 제거한 것은 아니다.

## 4. 일반 회원가입 처리 순서

1. 사용자가 가입 화면에서 정보를 입력한다.
2. 자동 가입 방지 검사를 수행한다. 실제 운영에는 캡차 연결이 필요하다.
3. 사용자가 이메일 인증번호 발송을 요청한다.
4. 서버가 입력, 캡차, 발송 제한과 가입 가능한 이메일인지 확인한다.
5. 서버가 6자리 인증번호를 생성하고 메일 업체에 발송을 요청한다. 업체 접수 성공은 메일함 도착 보장이 아니다.
6. 발송 요청이 성공하면 인증 기록을 저장하고 기존 미소비 인증 기록을 무효화한다. 현재 메일 발송과 DB 저장은 하나의 원자적 작업이 아니므로, 발송 후 DB 실패 시 사용자가 재요청해야 할 수 있다.
7. 사용자가 이메일 인증번호를 입력하면 서버가 요청 식별자, 요청 비밀값, 목적, 번호, 만료, 소비 여부와 실패 제한을 검사한다.
8. 성공하면 화면에 ‘이메일 인증되었습니다’를 표시한다. 이메일을 바꾸면 인증 상태를 해제하고 새 이메일로 다시 인증한다.
9. 가입 완료 시 비밀번호 일치 여부를 화면에서 검사하고, 서버는 인증 기록에 행 잠금을 잡은 뒤 인증 증거와 회원 입력을 다시 검증한다.
10. 비밀번호를 해시하고 회원을 생성한다. 인증 기록 소비도 같은 DB 트랜잭션에서 처리한다.
11. 두 작업이 모두 성공하면 가입 완료를 안내하고 로그인 화면으로 이동한다. 일반 가입 후 자동 로그인은 하지 않는다.

화면의 인증 완료 문구나 `verified` 값만으로 가입을 허용하지 않는다. 회원 저장이 실패하면 인증 소비도 함께 롤백한다. 원래 인증 유효기간이 연장되지는 않는다.

## 5. 이메일 인증 규칙

- 인증번호: 6자리 숫자, 서버의 보안 난수 기능으로 생성.
- 유효기간: 발급 기준 10분. 현재 구현에서는 최종 가입 시점에도 이 만료 시각을 검사한다.
- 재전송: 같은 이메일·목적에 최소 1분 간격.
- 재발급 성공 시 이전 번호와 이전 인증 결과는 사용할 수 없다.
- 잘못된 번호 입력: 이메일·목적별 15분 구간에 5회 제한. 재발송으로 실패 횟수가 초기화되지 않는다.
- 발송 요청: 현재 구현에서 접속 주소별 15분에 20회 제한.
- 가입, 비밀번호 재설정, 이메일 변경은 인증 목적을 구분한다.
- 인증 기록은 한 번만 가입 완료에 소비할 수 있다.
- 만료 검사는 매 요청에서 수행한다. 오래된 행을 실제로 삭제하는 작업과 별개다.

## 6. 기술 선택과 이유

| 선택 | 비교 대상 | 얻는 것 | 감수하는 점 및 선택 이유 |
|---|---|---|---|
| 기존 관계형 DB에 인증 기록 저장 | Redis TTL, 서버 메모리 | 저장소 하나로 운영하고 회원 생성·인증 소비를 같은 트랜잭션으로 처리 | 만료 검사와 오래된 기록 정리가 필요하다. 단기 프로젝트에서 별도 저장소 운영보다 이 부담이 작다고 판단 |
| PostgreSQL을 운영 DB로 사용 | 현재 개발용 SQLite | 관계·고유 제약과 트랜잭션을 갖춘 운영 구조 | 설치·연결과 운영 환경 검증이 필요하다. 현재 로컬 실행·자동 테스트는 SQLite이므로 PostgreSQL 검증 완료로 보지 않음 |
| 가입 인증 기록에 행 잠금 사용 | 조건부 갱신 | 인증 확인·회원 생성·인증 소비 순서를 명확하게 관리 | 같은 인증을 쓰는 요청은 대기한다. 이번 단기 프로젝트에서는 처리 흐름의 명확함을 우선하고 잠금 시간을 관리한다 |
| 메일 발송 결과를 기다린 후 응답 | 작업 큐와 별도 작업자 | 구성 요소가 적고 발송 요청 실패를 즉시 안내 가능 | 메일 지연만큼 요청이 대기한다. 자동 재시도 작업 운영을 추가하지 않는 선택이며, 현재 SMTP 호출에는 제한 시간이 있음 |
| Argon2id / argon2-cffi | bcrypt 등 비밀번호 해시 방식 | 비밀번호 추측에 필요한 계산·메모리 비용을 높임 | 서버도 비용을 부담하므로 배포 환경에서 비용 설정 확인 필요. 직접 해시 알고리즘을 만들지 않음 |
| 인증 완료 후 회원 생성 | 미인증 회원을 먼저 생성 | 정식 회원에 미완료 가입이 쌓이지 않음 | 인증 증거를 최종 가입까지 연결해야 한다. 임시 인증 기록 자체가 사라지는 것은 아님 |
| 회원 테이블에 Google 식별자 함께 보관 | 별도 로그인 수단 테이블 | 단기 프로젝트 구조와 조회를 단순화 | 다양한 제공자로 확장하기엔 제한적. 이번 범위에서는 확장보다 단순함을 우선 |

만료 기록 정리용 스케줄러는 현재 도입하지 않는다. 삭제 주기·보관 기간은 추후 정하되, 삭제가 늦어져도 만료된 인증을 허용하지 않는다.

### 6.1 가입 인증 기록의 동시 처리 — 행 잠금 선택 확정

**결정:** PostgreSQL의 `SELECT … FOR UPDATE`로 가입 인증 기록에 행 잠금을 잡는다. 회원 생성과 인증 사용 완료는 같은 DB 트랜잭션에서 처리한다.

#### 해결하려는 문제

사용자가 최신 이메일 인증번호로 인증을 끝낸 뒤 ‘가입 완료’를 빠르게 두 번 누르면, 같은 인증 결과를 사용하는 가입 요청이 동시에 들어올 수 있다. 두 요청이 모두 ‘아직 사용하지 않음’을 확인하고 처리하지 않도록 해야 한다.

‘최신 인증번호만 유효하다’는 규칙은 이전 번호를 거절하는 규칙이다. 이번 선택은 이미 인증된 최신 기록을 가입에 한 번만 사용하도록 하는 기술적 처리다.

#### 비교한 기술과 장단점

| 비교 항목 | 행 잠금 — 선택 | 조건부 갱신 — 비교 대안 |
|---|---|---|
| 방식 | 인증 기록을 잠그고 상태를 확인한 뒤 처리한다 | `UPDATE … WHERE … RETURNING`으로 유효하고 아직 사용하지 않은 기록만 사용 완료로 바꾼다 |
| 동시 요청 | 같은 기록을 잠그려는 다음 요청은 기다렸다가 앞 요청이 반영한 상태를 확인한다 | 변경 조건을 충족해 기록을 바꾼 요청만 가입을 진행한다. 다른 요청은 변경 결과가 없으면 진행하지 않는다 |
| 장점 | 인증 목적·만료·인증 완료·사용 여부 등 검사를 코드에서 순서대로 표현하고 실패 지점을 파악하기 쉽다 | 상태 확인과 변경을 하나의 DB 명령으로 묶을 수 있다. 조건을 SQL로 표현할 수 있는 경우 별도의 읽기 단계를 줄일 수 있다 |
| 단점 | 잠금 유지 중 같은 인증을 처리하는 요청은 대기한다. 느린 작업을 포함하면 잠금 시간이 늘어난다 | 유효 조건과 변경 결과의 성공·실패 판정을 정확히 작성해야 한다. 여러 검사와 오류 안내를 SQL 및 코드에 나누어 관리할 수 있다 |
| 주의점 | 잠금 범위와 유지 시간을 관리해야 한다 | 이 방식도 DB 내부에서 행 잠금을 사용하며 경합 시 대기가 발생할 수 있다. 잠금 없는 방식으로 보지 않는다 |
| 공통 조건 | 회원 저장과 인증 소비를 같은 트랜잭션으로 묶고, 이메일 고유 제약을 유지한다 | 회원 저장과 인증 소비를 같은 트랜잭션으로 묶고, 이메일 고유 제약을 유지한다 |

조건부 갱신도 올바르게 구현하면 같은 인증의 중복 사용을 방지할 수 있다. 행 잠금이 무조건 더 안전하거나 빠르다는 판단으로 선택한 것은 아니다.

#### 우리가 행 잠금을 선택한 이유

1. 이번 가입 흐름은 인증 완료·만료·목적·사용 여부 등 여러 조건을 확인하고 회원 생성까지 수행한다. 기록을 잠근 상태에서 조건을 확인하고 저장하는 순서가 현재 코드와 학습 목적에 맞는다.
2. 단기 프로젝트에서는 처리 과정을 이해하고, 실패한 단계를 설명하며, 트랜잭션으로 함께 취소되는 동작을 검증하기 쉬운 구조를 우선한다.
3. 이 선택으로 같은 인증 기록을 사용하는 요청의 대기를 감수한다. 대기 시간과 처리량을 측정하지 않았으므로 성능상 우월하다고 주장하지 않는다.

#### 선택한 처리 순서

1. 가입 요청의 인증 기록을 `SELECT … FOR UPDATE`로 조회하고 잠근다.
2. 요청 비밀값, 인증 목적, 인증 완료, 유효기간 및 소비 여부를 검사한다.
3. 회원 정보를 검증하고 비밀번호 해시와 회원 정보를 저장한다.
4. 인증 기록을 사용 완료로 변경한다.
5. 두 저장 작업이 모두 성공하면 커밋하고 잠금을 해제한다. 같은 기록을 기다리던 요청은 사용 완료 상태를 확인하고 가입을 진행하지 않는다.
6. 중간에 실패하면 롤백하여 회원 생성과 인증 소비를 함께 취소하고 잠금을 해제한다. 인증이 여전히 유효하면 후속 요청이 다시 사용할 수 있다.

행 잠금은 같은 인증 기록의 사용을 조율한다. 서로 다른 인증 기록으로 같은 이메일 가입을 시도하는 경우에는 `members.email`의 고유 제약이 중복 회원 생성을 막는다.

#### 현재 구현과 검증할 사항

- 현재 코드의 `locked()`는 SQLAlchemy의 `with_for_update()`를 사용하며, 가입 시 `proof_record()`를 통해 적용된다.
- 현재는 인증 기록을 잠근 뒤 비밀번호 해시도 계산한다. 해시 계산 시간만큼 잠금이 유지되므로, 잠금 전에 해시를 계산하고 잠금 후 인증을 재확인하는 구성의 필요성을 추후 측정한다. 해당 최적화는 아직 적용하지 않았다.
- 현재 로컬 실행·자동 테스트는 SQLite 기준이다. PostgreSQL의 실제 행 잠금 및 동시 요청 동작은 아직 검증 완료가 아니다.
- PostgreSQL에서 같은 인증으로 가입 요청 두 개를 동시에 보내 한 번만 가입되는지 확인한다.
- 첫 요청의 회원 저장을 실패시켜 인증 소비가 롤백되고, 여전히 유효한 인증으로 후속 요청이 가입할 수 있는지 확인한다.
- 다른 인증 기록의 정상 가입도 함께 보내고, 잠금 유지 시간과 같은 기록을 기다리는 요청의 시간을 측정한다.

참고: [PostgreSQL 17 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS), [동시 갱신과 조건 재검사](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).

## 7. 회원가입 관련 DB 구조

### `members` — 정식 회원

| 컬럼 | 현재 타입·제약 | 의미 |
|---|---|---|
| `id` | 정수, 기본 키 | 바뀌지 않는 내부 회원번호 |
| `email` | 문자열 254, 필수·고유 | 로그인 이메일 |
| `password_hash` | 텍스트, NULL 허용 | 일반 가입 비밀번호 해시. Google 전용 회원은 없음 |
| `name` | 문자열 80, 필수 | 입력 이름 |
| `birth_date` | 문자열 10, NULL 허용 | 생년월일. 새 일반 가입에서는 API가 필수로 검사 |
| `nickname` | 문자열 40, NULL 허용 | 닉네임. 새 일반 가입에서는 API가 필수로 검사 |
| `phone` | 문자열 30, 필수 | 미인증 전화번호 |
| `google_subject` | 문자열 255, 고유·NULL 허용 | Google 계정 고유번호 |
| `created_at` | 정수 타임스탬프, 필수 | 가입 시각 |

기존 회원 데이터를 보존하기 위해 닉네임·생년월일 컬럼은 NULL을 허용한다. DB에는 비밀번호 해시 또는 Google 식별자가 있어야 한다는 검사 제약이 있다. 이메일이 바뀌어도 내부 회원번호는 유지한다.

### `email_verifications` — 임시 인증 기록

요청 ID, 회원번호(가입 전에는 없음), 이메일, 인증 목적, 코드 검증값, 요청 비밀값 검증값, 만료 시각, 인증 성공 시각, 소비 시각을 저장한다. 코드와 요청 비밀값 원문을 그대로 저장하지 않는다. 회원번호가 있는 경우 회원 테이블과 외래 키로 연결한다.

### 남용 제한 기록

이메일·목적 및 접속 주소별 제한 키, 횟수, 집계 시작 시각, 차단 종료 시각, 마지막 발송 시각을 관리한다. 인증 요청 행과 분리하여 재전송으로 실패 제한을 초기화하지 못하게 한다.

## 8. Google 가입과 계정 연결

- 서버가 Google 인증 결과와 이메일 검증 여부, 고유 식별자를 확인한다.
- Google 비밀번호를 수집하지 않는다. 별도의 서비스 비밀번호 생성도 강제하지 않는다.
- 기존 회원과 이메일이 같다는 이유만으로 자동 연결하지 않는다.
- 기존 계정으로 로그인한 상태에서 비밀번호 재확인과 연결 동의를 받은 뒤 연결한다.
- 계정 두 개의 데이터를 합치는 기능은 범위 밖이다.
- Google 전용 회원은 이메일 변경 UI를 숨기고 서버에서도 변경을 막는다.

**현재 구현 차이:** Google 신규 가입은 이름·전화번호만 추가로 받는다. 일반 가입에 추가한 닉네임·생년월일을 Google 가입에도 필수로 받을지와 추가 정보 화면은 아직 반영·확정되지 않았다. Google 서비스 키도 별도 설정이 필요하다.

## 9. 현재 반영 사항과 남은 작업

### 구현된 내용

- 가입 진입 시 이름·생년월일·닉네임·전화번호 및 인증·비밀번호 입력란 표시.
- 생년월일 저장과 잘못된 날짜·미래 날짜 거절.
- 비밀번호 확인과 입력 일치 안내.
- 자동 가입 방지와 이메일 인증 UI 분리.
- 이메일 인증 성공 문구, 인증 전 가입 차단, 서버 인증 증거 검증.
- 인증번호 재발송·만료·실패 제한, DB 이메일 중복 방지.
- 가입 정보 저장과 인증 소비를 같은 트랜잭션으로 처리.

### 연결·검증 또는 결정이 필요한 내용

- 숫자 이미지 캡차 제공자 선택 및 실제 연동. 현재 미연결.
- 실제 SMTP 계정 설정과 메일 수신 확인. 개발 모드는 인증번호를 화면에 표시하며 실제 소유 확인이 아니다.
- Google 서비스 설정 및 신규 가입 추가 수집 항목 정리.
- PostgreSQL 실행 환경에서 마이그레이션·동시 가입 검증.
- 만료 인증 기록의 보관 기간과 정리 방법.
- 개인정보 수집 안내·동의 항목과 생년월일 수집 목적의 구체화. 현재 화면에 구현됐다고 보지 않는다.

## 10. 완료 확인 기준

1. 일반 가입 화면에서 모든 항목을 처음부터 볼 수 있다.
2. 잘못된 생년월일이나 일치하지 않는 비밀번호로 가입할 수 없다.
3. 이메일 인증 없이 가입할 수 없고, 이메일을 바꾸면 재인증해야 한다.
4. 만료·이전·소비된 인증 기록으로 가입할 수 없다.
5. 같은 이메일로 동시에 가입해도 회원이 중복 생성되지 않는다.
6. 회원 저장 실패 시 인증 소비만 남지 않는다.
7. 운영 환경에서 캡차와 실제 이메일 인증을 각각 확인한다.
8. DB와 일반 API 응답에 비밀번호 원문·확인값이 저장되거나 노출되지 않는다.

이 항목은 검증 기준이며 모든 항목의 운영 환경 검증을 완료했다는 의미는 아니다.
