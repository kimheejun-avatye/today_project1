# 전체 설계 계획서

작성 기준: 2026-10-13. 기존 대화, 프로젝트 내 최종 회원가입 계획서, 현재 코드에 근거한다.

## 1. 프로젝트 개요

‘하루’는 회원이 캘린더에서 날짜를 선택해 일기·감정·할 일을 기록하는 웹 서비스다. 매일 반복하는 할 일과 일회성 할 일을 함께 관리하고, 선택한 일기를 공유하고 댓글을 남기는 최소 기능을 포함한다.

목표는 기능의 양보다 회원가입, 인증, CRUD, 데이터 관계와 동시 수정 문제를 일관되게 설계하고 각 선택의 이유와 한계를 설명하는 것이다. 단기 학습 프로젝트이며 현재 버전은 로컬 최소 구현이다. 운영 배포와 외부 서비스 검증 완료를 뜻하지 않는다.

## 4. 시스템 아키텍처

```text
브라우저: TypeScript 화면
  ├─ 캘린더·일기·회원 화면
  └─ sessionStorage: 회원·날짜별 작성 복구 사본
             │ /api 요청 + 쿠키
             ▼
API 서버: Python / FastAPI
  ├─ 입력 검사·인증·소유권·CSRF 검사
  ├─ 가입·토큰 교체·일기·반복 할 일 규칙
  ├─ SQLAlchemy를 통한 DB 접근
  ├─ 서버 생성 숫자 이미지·음성 캡차
  └─ SMTP / Google 연동
             │
             ▼
Supabase PostgreSQL: 현재 연결된 DB
  └─ 회원·인증·로그인·일기·할 일·댓글
```

프런트엔드는 TypeScript와 Vite, API는 Python FastAPI, 데이터 접근은 SQLAlchemy를 사용한다. 화면과 API는 현재 `frontend/`, `backend/`로 나뉘며 개발 시 별도 프로세스로 실행한다. API 내부 기능마다 별도 서버를 만드는 구조는 아니다. 현재 `backend/app/main.py`는 앱 시작과 라우터 등록을 담당한다. API는 `app/api/routes/`, 공통 업무 처리는 `app/services/`, DB 정의는 `app/models/`, 요청 검증은 `app/schemas/`에 나누어 관리한다.

개발 환경에서는 Vite가 `/api`를 FastAPI로 프록시한다. 운영은 HTTPS의 동일 출처에서 화면과 `/api`를 제공하는 역방향 프록시 구성을 목표로 한다. 호스팅 업체와 실제 배포 구성은 미정이다.

브라우저는 DB에 직접 연결하지 않는다. API가 로그인한 회원을 확인하고 요청 대상 소유권과 입력을 검증한다. DB는 관계·중복·일부 상태 제약을 보장한다. 외래키는 접근 권한 검사를 대신하지 않는다.

Redis, 메시지 큐, 별도 작업자는 현재 도입하지 않는다. 인증·제한 상태도 관계형 DB에 두어 운영 구성과 가입 트랜잭션을 단순하게 유지한다. 대신 만료 데이터 정리와 DB 부하를 관리해야 한다.

## 5. 회원가입 설계

**입력 항목, 인증번호 정책, 캡차, Google 가입·계정 연결, 가입 완료 조건은 [최종 회원가입 계획서](최종%20회원가입%20계획서.md)를 그대로 따른다.**

전체 시스템에서는 이메일 인증 후 회원을 생성하고, 회원 생성과 인증 기록 소비를 한 DB 트랜잭션으로 묶는다. 이름·닉네임은 일반·Google 신규 가입에서 수집한다. 숫자 이미지 캡차와 개발용 개인정보 필수 동의를 구현했다. Gmail 연결 테스트 메일의 실제 수신과 Google 로컬 클라이언트 설정·버튼 표시를 확인했다. 홈페이지의 실제 인증번호 가입 흐름, 실제 Google 계정 인증과 운영 개인정보 정책 확정은 남아 있다.

## 6. 로그인과 접근 권한

- 접근 토큰은 15분, 재발급 가능 기간은 최초 로그인부터 7일이다. 현재 구현은 마지막 접근 토큰도 로그인 종료 시점을 넘지 않게 제한한다.
- 한 회원은 하나의 로그인만 유지한다. 새 로그인 성공, 로그아웃, 비밀번호 재설정 시 기존 로그인 상태를 종료한다.
- 인증 요청마다 토큰과 서버 로그인 상태를 함께 검사한다. 토큰을 쓰지만 서버 상태가 없는 구조는 아니다.
- 재발급 토큰은 교체하고 직전 토큰의 5초 내 재시도에는 같은 결과를 반환하는 최소 구현을 사용한다. 유예 응답은 암호화해 보관한다. 이후 옛 토큰 재사용은 해당 로그인 재발급을 차단한다.
- 운영 쿠키는 HttpOnly·Secure를 사용한다. 현재 구현은 SameSite=Lax, Origin 검사와 로그인 세션에 연결된 CSRF 검사를 사용하며 배포 환경에서 재검증한다.
- 개인 일기·할 일 변경은 로그인 회원과 소유자가 일치해야 한다. 공유 조회와 댓글은 별도 공개 조건을 적용한다.

### 6.1 인증 구조 선택 — JWT와 서버 로그인 기록 확인 병행

**선택 확정: 2026-10-13. 접근용 JWT를 검증한 뒤, JWT의 로그인 번호로 기존 `login_sessions` 기록을 조회해 현재 로그인 상태도 확인한다.** 재발급용 토큰은 현재의 무작위 문자열 형식과 교체 이력 관리를 유지한다.

선택 이유는 이미 서버에서 로그인 기록을 관리하고 있기 때문이다. 현재 JWT 구조를 유지하면서 그 기록을 활용해 로그아웃·새 기기 로그인·비밀번호 재설정 시 이전 로그인의 접근을 차단한다. 로그인 종료가 DB에 반영된 뒤 권한 검사를 받는 요청부터 거절한다. 이미 처리 중인 요청까지 자동으로 취소한다는 의미는 아니다.

| 비교한 구조 | 얻는 것 | 감수하는 점 및 이번 판단 |
|---|---|---|
| 서버 세션 ID로 로그인 기록 조회 | 로그인 유지·종료를 서버에서 관리하며 동일한 기능 요구를 구현 가능 | 매 요청 세션 상태 확인 필요. 가능한 대안이지만 이번에는 현재 JWT 구현을 유지하기로 선택 |
| JWT의 서명·만료만 검사 | 로그인 기록 조회 없이 토큰 자체를 검증 가능 | 별도 취소 상태 전달·검사 장치가 없으면 만료 전의 복사본을 즉시 차단하지 못함. 이미 정한 즉시 종료 정책을 충족하지 못하므로 선택하지 않음 |
| **JWT 검증 + 서버 로그인 기록 확인 — 선택 확정** | 기존 로그인 기록을 활용한 즉시 접근 차단, 현재 JWT 발급·검증·재발급 흐름 유지 | 매 요청 JWT 검증과 로그인 기록 조회가 모두 필요하며, 서명 키·토큰 만료·재발급 교체 이력도 관리해야 함 |

현재 선택은 기존 구현과 로그인 기록을 활용해 종료 정책을 충족하는 선택이다. JWT가 서버 세션보다 성능이나 확장성에서 우수하다고 검증한 결과는 아니며, 로그인 기록 조회를 없애는 장점은 얻지 않는다. JWT를 직접 구현·검증하는 학습 효과는 유지한다. 순수한 서버 세션 방식으로도 같은 서비스 기능을 만들 수 있다는 점을 함께 기록한다.

## 7. 주요 화면과 데이터 흐름

1. 로그인 후 캘린더에서 해당 월의 일기를 조회한다.
2. 날짜를 선택하면 해당 날짜의 일기와 할 일을 각각 조회한다.
3. 일기 저장 요청은 본문·감정·상태·버전을 전달한다. API는 소유권과 기존 버전을 검사하고 저장한다.
4. 오래된 버전의 저장은 충돌로 거절한다. 화면은 작성 내용을 유지하고 새 기록을 확인하도록 안내한다.
5. 반복 할 일은 적용 기간으로 조회하며, 아직 저장된 행이 없으면 미완료 항목으로 표시한다. 체크 시 날짜별 행을 저장한다.
6. 인증이 만료되면 재발급을 시도하고, 재로그인이 필요하더라도 작성 내용을 지우지 않는다. 다른 기기 복구는 서버에 저장된 초안에 한한다.

## 8. API 구성

아래 경로는 현재 `backend/app/api/routes/` 기준이다. 요청·응답 필드의 실행 가능한 명세는 개발 서버의 `/docs`에서 확인한다.

| 기능 | 메서드·경로 |
|---|---|
| 인증번호 요청·확인 | `POST /api/auth/email/request`, `POST /api/auth/email/verify` |
| 이미지 캡차 발급·확인 | `POST /api/auth/captcha`, `POST /api/auth/captcha/verify` |
| 가입·로그인·재발급·로그아웃 | `POST /api/auth/signup`, `/api/auth/login`, `/api/auth/refresh`, `/api/auth/logout` |
| Google·비밀번호 복구 | `POST /api/auth/google/prepare`, `POST /api/auth/google`, `POST /api/auth/password/reset` |
| 본인 정보 | `GET /api/me`, `PATCH /api/me`, `POST /api/me/email` |
| 월별 일기 | `GET /api/diaries?month=YYYY-MM` |
| 날짜별 일기 | `GET`, `PUT`, `DELETE /api/diaries/{day}` |
| 할 일 생성·완료 | `POST /api/tasks`, `PATCH /api/tasks` |
| 날짜별 할 일·삭제 | `GET /api/tasks/{day}`, `DELETE /api/tasks/{task_id}` |
| 반복 종료 | `POST /api/recurring/{rid}/stop?day=YYYY-MM-DD` |
| 공유·댓글 | `GET /api/community`, `GET/POST /api/community/{did}/comments`, `DELETE /api/comments/{cid}` |

소유자는 클라이언트의 회원번호가 아닌 서버 인증 결과로 정한다. 완료 요청은 상태 반전 대신 원하는 `completed` 값을 보낸다. 입력 오류·인증 실패·접근 불가·편집 충돌을 구분하며 화면은 저장 실패를 성공으로 표시하지 않는다.

현재 월 조회는 일기 본문도 반환한다. 캘린더용 날짜·감정·상태 요약만 반환하는 응답 최적화는 후속 제안이며 이미 구현된 것으로 보지 않는다.

## 9. DB 설계 방향

운영 DB는 PostgreSQL을 기준으로 하고, 세부 사항은 [DB 설계서](DB%20설계서.md)를 따른다. 회원 관계, 하루 한 일기, 반복별 날짜 중복 방지, 가입 원자성을 DB 제약과 트랜잭션으로 표현한다.

현재 모델은 캡차 확인 기록을 포함한 10개 테이블이다. 로컬에서 실행하는 API도 Supabase PostgreSQL에 연결한다. SQLite는 이전 원본·백업과 별도 테스트 용도로 남아 있다. Supabase는 DB를 제공하고, 회원가입·로그인은 기존 FastAPI가 담당한다. Supabase Auth로 교체한 구조가 아니다.

2026-10-13 변경 사항은 다음과 같다.

- 테이블과 외래키 관계는 유지하고 `members.birth_date`, `members.phone`, `members.created_at`, `login_sessions.created_at`을 제거했다. 동의·만료·교체·댓글 작성 시각 등 기능에 필요한 시각은 유지한다.
- 이름은 내부 회원 정보, 닉네임은 공개 작성자 표시로 구분한다. 기존 회원의 닉네임이 없으면 `익명`으로 표시한다. 회원가입 수집·동의 정책은 최종 회원가입 계획서를 따른다.
- 만료 인증 기록은 기준 시점 이후 24시간 보관하고 매시간 정리한다. 활성 로그인에 속한 이전 재발급 토큰은 재사용 탐지를 위해 유지하며, 5초 유예가 지난 응답 암호문은 별도로 비운다. 대상별 기준은 DB 설계서 9절을 따른다.
- 10개 테이블의 RLS를 유지하고 브라우저의 anon·authenticated 역할 접근을 차단한다. FastAPI의 DB 연결과 API 소유권 검사로 접근을 관리한다. RLS만으로 사용자별 권한 검사가 완성되는 것은 아니다.

데이터 이전·컬럼 제거·정리 예약 적용은 완료했다. 정리 함수 수동 최초 실행은 성공했으나 예약 실행 결과와 로그인 후 전체 기능·동시성 검증은 별도로 남아 있다. 상세 적용 기록은 DB 설계서 12절과 [Supabase 연결 진행 상태](backend/SUPABASE_SETUP.md)를 따른다.

## 10. 구현·검증 단계

| 단계 | 결과물·완료 조건 | 현재 상태 |
|---|---|---|
| 정책·문서 정리 | 전체·회원가입·DB 전문 문서 연결 | 이번 문서 정리 반영 |
| 로컬 기능 | 가입, 로그인, 날짜별 기록, 공유 흐름 | 최소 구현 존재, 과거 테스트 결과는 README 참고 |
| DB 전환 검증 | PostgreSQL 마이그레이션, 기존 데이터 보존, 동시성 검사 | Supabase 데이터 이전·연결 전환·불필요 컬럼 제거 완료. 임시 PostgreSQL 가입 경쟁·롤백 검사 통과. 전환 후 전체 기능·운영 검증은 남음 |
| 외부 연결 | SMTP 수신, Google 검증 | Gmail 테스트 메일 실제 수신, Google 로컬 클라이언트 연결·버튼 표시 확인. 실제 홈페이지 가입 인증과 Google 계정 인증 검증은 남음; 이미지 캡차는 서버 자체 구현 |
| 정책 마무리 | 반복 이력, 공유 방식, 삭제·보관, 시간대 | 일부 미정 |
| 운영 준비 | HTTPS, 비밀키, 백업·복구, 배포 환경 권한 검사 | 미완료 |

중요 검증은 다른 회원 기록 접근 차단, 동시 가입 중복 방지, 인증 소비 롤백, 단일 로그인, 토큰 교체 경쟁, 일기 버전 충돌, 날짜별 완료 독립성이다. 문서 작성 자체는 이 검증을 통과했다는 의미가 아니다.

## 11. 남은 결정과 한계

- 반복 이름 변경 전후의 과거·미래 항목 처리와 종료 전에 생성한 미래 행 처리.
- 공유 원본 공개 또는 복사본 방식, 공유 취소 후 댓글 보관.
- 회원 탈퇴와 일기·댓글 등 서비스 데이터 및 백업의 삭제·보관 기간. 인증 기록의 24시간 보관·매시간 정리는 확정·적용했으며 예약 실행 점검은 남아 있다.
- ‘오늘’을 계산할 시간대와 자정 경계 처리. 사용자 선택 날짜와 서버 생성 시각을 구분한다.
- PostgreSQL 날짜·시간 자료형 전환, 마이그레이션과 실제 부하·동시성 검증.
- 회원가입의 미정 사항은 최종 회원가입 계획서의 남은 작업 목록을 따른다.
