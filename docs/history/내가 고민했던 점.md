# 내가 고민했던 점

작성일: 2026-10-13

## 이 문서를 쓰는 목적

회사 첫날 과제는 웹사이트 구현, DB 설계, API 서버 구축, 회원가입이었다. 작은 일기·커뮤니티 서비스는 이를 배워 보기 위한 배경이다. 나는 기능 목록이나 발표용 문장보다 기술이 무엇이고 어떻게 동작하는지 이해하고 싶었다. 시니어가 “왜 이렇게 했어요?”라고 물었을 때, 비교한 대안과 선택의 한계까지 설명할 수 있는 것이 목표였다.

이 문서는 구현 순서가 아니라 대화에서 실제로 질문하고 판단한 내용을 돌아보는 기록이다. 기존 [회원가입·로그인 설계 계획서](회원가입-설계-계획서.md)와 대화 요약을 바탕으로 작성했다. 아래의 ‘결정’은 설계상 합의이며 구현이나 검증이 끝났다는 뜻은 아니다. 설명을 위해 나온 제안과 아직 정하지 않은 사항은 따로 표시했다.

## 1. 정보를 받는 것과 인증하는 것은 어떻게 다른가?

**고민한 질문:** 이름과 전화번호도 받아 보고 싶은데, 이메일 인증을 하면 이 정보까지 확인한 것으로 볼 수 있을까? 문자 비용이 부담되는 상황에서 어떤 인증을 실제로 구현할까?

**비교한 대안:** 문자 인증을 붙이는 방법과 실제 이메일 인증을 구현하는 방법을 비교했다. 학습용이라고 가짜 문자 발송으로 끝내기보다 실제로 동작하는 이메일 인증을 선호했다.

**판단과 상태 — 결정:** 이름과 전화번호 수집은 학습 범위에 포함하고, 이번에는 문자 인증을 사용하지 않는다. 이메일 인증으로 확인하는 것은 해당 메일을 확인할 수 있는지다.

**감수한 한계:** 이름을 입력했다고 실명 확인이 되지는 않는다. 전화번호도 입력값일 뿐 소유 여부를 확인한 번호가 아니다. 이메일 인증 역시 실제 신원이나 한 사람당 하나의 계정을 보장하지 않는다.

## 2. 이메일의 링크를 누르게 할까, 코드를 입력하게 할까?

**고민한 질문:** 인증 링크와 인증번호는 사용 흐름이 어떻게 다를까? 링크가 탈취될 수 있다면 코드를 함께 보내면 더 확실해질까?

**비교한 대안:** 메일의 링크를 눌러 인증을 마치는 방식과, 메일에서 코드를 확인하고 가입하던 홈페이지에 입력하는 방식을 비교했다. 링크와 코드를 같은 메일에 함께 보내는 방법도 이야기했다.

**판단과 상태 — 결정:** 이메일로 받은 코드를 홈페이지에 입력하는 방식으로 진행한다. 다른 기기에서 메일을 확인해도 가입하던 화면에서 계속할 수 있다.

**이해한 한계:** 같은 메일에 있는 링크와 코드는 독립된 두 인증요소가 아니다. 메일을 읽을 수 있는 사람이 둘 다 볼 수 있으므로, 둘을 함께 요구한다고 메일 탈취 문제를 해결했다고 말할 수 없다. 코드 방식도 메일 접근 자체가 탈취된 상황까지 해결하지는 않는다.

## 3. 인증 전에도 회원을 만들까? 임시 기록은 어디에 둘까?

**고민한 질문:** 아직 이메일을 확인하지 않은 신청과 정식 회원을 어떻게 구분할까? 잠깐 필요한 인증 정보를 저장하려고 Redis까지 도입해야 할까?

**비교한 대안:** 인증 전 신청을 회원으로 관리하는 흐름과, 임시 인증 기록을 따로 두고 인증 후 회원을 만드는 흐름을 비교했다. 임시 기록 저장소로는 기존 DB와 추가 Redis를 고려했다.

**판단과 상태 — 결정:** 인증 기록은 기존 DB의 별도 테이블에 둔다. 이메일 인증 후 나머지 정보를 제출할 때 정식 회원을 생성한다. 이번 범위에서는 저장소를 추가로 운영하는 부담을 줄이기로 했다.

**감수한 한계와 미정:** DB에 기록했다고 만료 처리가 자동으로 해결되지는 않는다. 만료 요청을 거절하고 오래된 기록을 정리해야 한다. 인증 후 이메일을 바꾸면 재인증해야 한다. 인증 성공을 최종 가입 요청까지 어떻게 연결할지, 회원 생성과 인증 결과 소비를 어떻게 함께 처리할지는 구현 전에 정해야 한다.

## 4. 메일을 보냈다는 말은 어디까지 믿을 수 있을까?

**고민한 질문:** 발송 요청 후 언제 화면에 결과를 보여 줄까? 메일 업체가 성공을 반환하면 사용자의 메일함에 도착한 것일까?

**판단과 상태 — 결정:** 초기에는 메일 업체의 발송 요청 결과를 기다린 뒤 응답하는 단순한 방식으로 진행한다. 구현과 요청 실패 안내가 단순해지는 점을 선택 이유로 삼았다.

**감수한 한계:** 외부 업체가 느리면 가입 요청도 영향을 받는다. 업체의 접수 성공과 메일함 배달 성공은 다르다. 따라서 ‘요청이 접수됐다’는 결과만으로 사용자가 메일을 받았다고 단정할 수 없다.

**미정:** 업체, 기다리는 시간의 상한, 응답을 못 받아 실제 접수 여부가 불명확할 때의 재시도 정책은 남아 있다. 별도 발송 구조를 이미 도입한 것으로 기록하지 않는다.

## 5. 재전송과 중복 확인은 편의만 생각하면 될까?

**고민한 질문:** 인증번호를 다시 보내면 이전 번호도 인정할까? 실패 횟수도 새로 시작할까? 가입 전에 이메일 중복을 조회하면 중복 회원 생성을 막은 것일까?

**비교와 판단 — 결정:** 새 코드를 발급하면 이전 코드는 거절한다. 재전송해도 일정 시간 동안의 인증 실패 횟수는 유지한다. 재전송으로 입력 제한을 계속 초기화할 수 있게 두지 않기 위해서다. 자동 가입 방지는 모든 가입자에게 캡차를 적용하는 방향이다.

**감수한 한계:** 늦게 도착한 이전 메일의 코드를 입력하면 실패할 수 있다. 캡차는 정상 사용자에게도 절차를 추가하며, 캡차 하나로 모든 남용이 해결되지는 않는다.

**설명에서 구분한 점:** 사전 중복 조회는 사용자 안내에 도움이 되지만, 조회 직후 다른 가입 요청이 처리될 수 있다. DB 고유 제약은 이런 동시 요청에서도 중복을 막는 역할이다. 두 가지는 역할이 다르다. “이미 가입한 이메일”이라는 안내는 편리하지만 가입 여부를 외부에 알려 주기도 한다.

**미정:** 코드 길이·만료·실패 제한 수치, 캡차 제품과 적용 위치, 이메일 비교 규칙, 중복 충돌 처리와 가입 여부 안내 정책은 정하지 않았다.

## 6. Google 가입은 무엇을 믿고, 기존 회원과 어떻게 연결할까?

**고민한 질문:** Google로 로그인할 때 우리 DB가 Google 비밀번호를 확인하는 것일까? 같은 이메일이면 기존 회원과 바로 합쳐도 될까?

**이해한 동작:** Google이 사용자를 인증하고, 우리 서버는 그 인증 결과를 검증한다. 우리 서비스가 Google 비밀번호를 받아 비교하는 구조가 아니다. 검증된 제공자 계정 식별자로 내부 회원과의 연결을 찾는다. 필요한 이름이나 전화번호가 부족하면 추가로 확인한다.

**비교한 대안:** 이메일 일치만으로 자동 연결하는 방법과, 기존 계정에 대한 권한을 다시 확인하고 동의를 받아 로그인 수단을 연결하는 방법을 비교했다.

**판단과 상태 — 결정:** 자체 가입과 Google 가입을 지원하되, 이메일 일치만으로 자동 연결하지 않는다. 기존 계정 재확인과 동의 후 같은 내부 회원에 Google 로그인 수단을 추가한다. 기존 자체 계정은 비밀번호 재확인을 거친다.

**감수한 한계와 미정:** 연결 절차가 늘어난다. Google이 제공하는 이메일 검증 정보를 어떤 조건에서 인정할지, 연결 해제나 계정 복구는 아직 정하지 않았다. 이미 따로 만들어진 두 회원의 게시글과 데이터를 병합하는 일은 로그인 수단 연결과 다른 문제다.

## 7. 작은 서비스인데 왜 세션 대신 토큰을 선택했을까?

**고민한 질문:** 이 서비스에는 무엇이 더 단순할까? 토큰을 쓰는 이유를 “더 안전하고 빠르다”라고 설명해도 될까?

**비교한 대안:** 서버에서 로그인 상태를 관리하는 세션 방식과 서명된 토큰을 발급·검증하는 방식을 비교했다. 작은 서비스에서는 세션이 로그인 상태 관리와 즉시 취소를 더 단순하게 만들 수 있다는 설명을 받아들였다.

**판단과 상태 — 결정:** 토큰 발급, 검증, 만료, 재발급, 취소를 직접 설계하며 배우기 위해 서명된 토큰 방식을 선택했다. 이번 선택의 근거는 학습 목적이다.

**감수한 한계:** 이미 발급한 토큰을 만료 전에 취소하거나 재발급 상태를 관리하는 일이 복잡해질 수 있다. 토큰이 무조건 더 안전하거나 빠르다는 주장은 선택 이유에서 제외했다. 서명 검증도 탈취된 정상 토큰을 공격자가 사용하는 문제까지 구분해 주지는 않는다.

## 8. 로컬 스토리지와 HttpOnly 쿠키는 실제 요청에서 어떻게 다른가?

**고민한 질문:** 둘 다 내 브라우저에 저장한다면 차이는 무엇일까? JavaScript가 읽는다는 것은 누가 무엇을 한다는 뜻일까?

**비교한 대안:** 로컬 스토리지는 브라우저에서 실행되는 코드가 토큰을 읽어 요청의 인증 헤더에 붙이는 흐름으로 이해했다. HttpOnly 쿠키는 서버가 설정하고 브라우저가 조건에 맞는 요청에 자동으로 붙이며, 페이지 JavaScript에서는 값을 직접 읽지 못한다.

**판단과 상태 — 결정:** 로그인 토큰은 HttpOnly 쿠키에 보관한다. 화면 코드가 토큰 값을 직접 읽을 필요가 없으므로, 악성 스크립트가 토큰 값을 직접 읽어 빼내는 경로를 줄이기로 했다.

**감수한 한계와 미정:** 쿠키 자동 전송에 따른 CSRF 방어 책임이 생긴다. HttpOnly가 XSS 자체나 브라우저에서 사용자 권한으로 보내는 악성 요청까지 막지는 않는다. 쿠키의 구체적인 보안 속성과 CSRF 방어 방식은 후속 설계 사항이다. 쿠키를 쓴다고 인증 방식이 서버 세션으로 바뀌는 것도 아니다.

## 9. 토큰 두 개의 시간은 합쳐지는가? 글을 오래 쓰면 어떻게 되는가?

**고민한 질문:** 접근용과 재발급용 토큰은 각각 무엇을 위한 것일까? 시간을 합쳐 로그인 시간이 되는가? 몇 시간 동안 글을 쓰다가 만료되면 글을 잃는가?

**이해한 구분:** 접근용 토큰은 일기 전용이 아니라 인증이 필요한 API 요청에 공통으로 사용한다. 사용자 확인 후 실제 접근 권한은 별도로 검사한다. 재발급용 토큰은 새 접근용 토큰을 받는 데 사용한다. 두 유효기간을 더해 ‘30분’이 되는 구조가 아니며, 갱신은 기존 접근용 토큰의 수명을 늘리는 것이 아니라 새 토큰을 받는 것이다.

**판단과 상태 — 결정:** 두 종류의 토큰을 사용하는 방향으로 진행한다. 작성 중 인증이 만료되어도 글을 잃지 않도록 한다. 재발급할 수 있으면 저장을 이어 가고, 재발급이 거절되면 글을 보존하면서 재로그인을 안내한다.

**미정과 설명 제안:** 접근용 15분, 재발급용 7일은 예시다. 확정값이나 업계 평균으로 받아들이지 않았다. 갱신 시점, 최대 로그인 유지 기간, 구체적인 재로그인 화면도 미정이다. 재로그인 후 동일 회원인지 확인하고 저장 재시도 중 중복을 막는 것은 글 보존 원칙을 구현하기 위한 보완 초안이다.

## 10. 브라우저 복구 사본, 임시 저장, 등록은 같은 것일까?

**고민한 질문:** 작성 중인 글을 어디에 남겨야 할까? 다른 기기에서도 이어 쓰려면 무엇이 필요한가? 30분마다 자동 저장하는 것이 적절할까?

**비교와 판단 — 결정:** 브라우저의 자동 복구용 사본과 서버 DB의 초안을 구분한다. ‘임시 저장’ 버튼으로 서버 DB에 초안을 저장하고, ‘등록’은 내용을 저장하면서 작성 완료 상태로 처리한다. 서버 초안은 같은 계정으로 다른 기기에서 이어 쓰기 위한 선택이다.

**감수한 한계:** 다른 기기에서는 마지막으로 서버에 저장된 내용까지만 복구할 수 있다. 브라우저에만 있는 변경분이 자동으로 전달되는 것은 아니다. 작성 완료와 커뮤니티 공개 여부도 별개다.

**내가 바로잡은 부분:** 30분은 적절한지 의견을 물었던 값이지 결정한 주기가 아니었다. 설명 중 나온 30초 역시 제안이다.

**미정:** 브라우저 저장 기술과 주기, 서버 자동 저장 주기, 브라우저 사본과 서버 초안의 충돌, 여러 탭·기기에서의 편집, 공용 기기에서의 노출과 삭제 정책은 남아 있다. 초안과 완료 상태를 같은 DB에서 표현할 수 있다는 설명도 최종 스키마 확정은 아니다.

## 11. 리프레시 토큰 재사용은 공격인가, 정상 재시도인가?

**고민한 질문:** 토큰을 한 번 쓰고 교체하면 탈취 문제를 해결할 수 있을까? 서버가 교체했지만 응답이 유실되어 사용자가 이전 토큰으로 다시 요청하면 어떻게 할까?

**판단과 상태 — 회전 결정:** 재발급 성공 시 새 접근용 토큰과 새 리프레시 토큰을 발급하고, 이전 리프레시 토큰을 교체한다. 같은 값을 유효기간 내내 계속 쓰게 두지 않고 이미 사용한 값의 재사용을 제한하려는 선택이다. 아직 사용되지 않은 토큰의 탈취까지 막는 것은 아니다.

**내가 제안하고 다시 검토한 기준:** IP나 브라우저가 같으면 정상 재시도로 볼 수 있지 않을까 생각했다. 하지만 공유 IP, 네트워크 이동, 정보 위조 가능성 때문에 같은 요청자임을 확정하는 증거로 쓰기 어렵다는 한계가 있었다.

**내가 지적한 설명의 한계:** DB에 토큰 사용 기록을 남기면 ‘이미 사용했다’는 사실은 알 수 있다. 그러나 그것만으로 공격자의 재사용과 정상 사용자의 재시도를 구분할 수는 없다. 사용 기록을 구분 문제의 해답처럼 설명해서는 안 된다고 지적했다.

**비교한 대안:** 사용된 토큰이 다시 오면 엄격히 차단하는 방법과, 정상적인 응답 유실·재시도를 위해 짧게 허용하는 방법을 비교했다. 전자는 정상 사용자도 재로그인해야 할 수 있고, 후자는 허용 시간 동안 공격자의 재사용 가능성도 남긴다.

**판단과 상태 — 5초 유예 결정:** 불필요한 재로그인을 줄이기 위해 교체 시점부터 5초 동안 직전 리프레시 토큰의 재시도를 제한적으로 허용한다. 반복 요청으로 유예 시간이 늘어나지는 않는다. 이 수치는 프로젝트 초기 정책이며 업계 공통 기준은 아니다.

**판단과 상태 — 유예 이후 차단 결정:** 유예가 지난 뒤 이미 사용한 토큰이 다시 제출되면, 해당 로그인에서 발급·교체된 리프레시 토큰 전체의 재발급 권한을 취소한다. 현재 새 토큰을 가진 쪽도 추가 재발급을 받을 수 없게 한다. 다른 기기의 별도 로그인까지 모두 차단하는 정책은 아니다.

**감수한 한계와 미정:** 5초 안의 요청이 정상이라는 것을 증명한 것은 아니다. 유예 안에서 어떤 결과를 돌려줄지, 동시 요청을 어떻게 일관되게 처리할지는 정하지 않았다. 이미 발급된 접근용 토큰을 즉시 무효화할지도 미정이다. 정책을 정한 것과 이를 정확히 구현한 것은 구분해야 한다.

## 내가 지적하거나 대화에서 바로잡은 오해

| 내용 | 정리한 이해 |
|---|---|
| “사용 기록이 있으면 공격과 재시도를 구분한다” | 내가 지적한 핵심이다. 기록은 재사용 탐지에 도움이 되지만 요청자의 의도까지 알려 주지 않는다. |
| “30분 자동 저장을 결정했다” | 의견을 물은 값을 결정으로 기록하면 안 된다. 30분과 30초 모두 미확정이다. |
| “해시는 비밀번호에만 쓴다” | 설명이 정정됐다. 랜덤 리프레시 토큰의 DB 검증값 보호에도 활용할 수 있다. 구체적인 저장 방식은 별도 결정이다. |
| “JavaScript가 저장한다” | JavaScript는 언어이고, 브라우저에서 실행되는 코드가 저장소를 읽고 쓴다는 뜻이다. |
| “HttpOnly면 토큰 탈취와 악성 요청을 모두 막는다” | 페이지 코드의 값 직접 읽기를 제한한다. XSS·CSRF 등 나머지 책임은 남는다. |
| “서명을 확인했으니 사용자가 정당하다” | 위조·변조 검사와 탈취된 정상 토큰의 사용 문제는 다르다. |
| “접근용과 재발급용 시간을 합치면 로그인 시간이다” | 역할과 만료 기준이 다르며, 기존 토큰의 시간이 저절로 늘어나지 않는다. |
| “같은 이메일의 회원을 연결하면 데이터 병합도 끝난다” | 기존 회원에 로그인 수단을 추가하는 것과 별도 회원들의 데이터를 합치는 것은 다르다. |

## 결정 요약

- 실제 이메일 코드를 홈페이지에 입력하고, 인증 후 정식 회원을 생성한다. 이름·전화번호 입력은 별도 신원 인증으로 취급하지 않는다.
- 인증 기록은 기존 DB의 별도 테이블에 둔다. 메일 업체 요청 결과를 기다리는 단순한 발송 흐름을 선택했다.
- 코드 재발급 시 이전 코드를 거절하고 실패 횟수는 유지한다. 모든 가입자에게 캡차를 적용하는 방향이다.
- 자체 가입과 Google 가입을 지원한다. 이메일 일치만으로 자동 연결하지 않고 기존 계정 재확인과 동의를 거친다.
- 학습 목적으로 서명된 토큰을 선택하고 HttpOnly 쿠키에 보관한다. 접근용과 재발급용을 구분한다.
- 리프레시 토큰은 회전한다. 직전 토큰에 교체 시점부터 5초의 고정 유예를 두며, 이후 사용된 토큰 재사용 시 해당 로그인 계열의 재발급 권한을 모두 취소한다.
- 인증 만료로 작성 중인 글을 잃지 않도록 한다. 브라우저 복구 사본과 서버 초안을 구분하고, 수동 임시 저장은 서버 DB에 한다.

## 남은 질문

1. 이메일 인증 결과를 최종 가입까지 어떻게 연결하고 한 번만 사용하게 할까? 동시 가입과 DB 고유 제약 충돌은 어떻게 처리할까?
2. 인증·발송 제한 수치, 메일 업체, 캡차 제품을 어떻게 정할까? 가입 여부 안내의 편의성과 정보 노출은 어떻게 조정할까?
3. Google의 이메일 검증을 언제 인정할까? 연결 해제와 계정 복구는 어떻게 처리할까?
4. 토큰 형식·라이브러리·검증 정책과 두 토큰의 수명은 어떻게 정할까? 회전 후에도 넘지 못하는 최대 유지 기간을 둘까?
5. 5초 유예 안의 중복 요청에 어떤 결과를 돌려줄까? 다중 탭과 동시 재발급을 어떻게 처리할까?
6. 재사용 탐지, 로그아웃, 비밀번호 변경, 탈퇴 시 접근용 토큰은 언제까지 유효하게 둘까?
7. 쿠키 설정과 CSRF 방어를 배포 환경에 맞게 어떻게 구성할까?
8. 글의 자동 보존 주기, 서버·브라우저 사본 충돌, 기기·계정별 분리와 삭제를 어떻게 처리할까?

이 질문들은 아직 답을 정하지 않은 부분이다. 선택 이유를 설명할 때에도 확정한 정책, 설명을 위한 제안, 실제 구현 결과를 구분해서 말해야 한다.
