# 우리가 고민한 설계 결정

이 문서는 현재 결론을 요약한 것이다. 질문과 대안 비교, 결정이 바뀐 과정은 [고민과 설계 과정 원본](history/README.md)에 별도로 보존한다. 요약본이 원본을 대체하지 않는다.

초기 메모의 질문을 현재 선택·대안·한계로 정리했다. 과거 미확정 아이디어를 구현된 기능으로 설명하지 않는다.

| 고민 | 현재 선택과 이유 | 대안·한계 |
|---|---|---|
| 사용자가 직접 쓸 만큼 간단한가 | 날짜별 일기·감정·오늘 할 일·반복 할 일 중심 | 공유 기능이 개인 기록 흐름을 복잡하게 만들지 않아야 함 |
| 이메일 번호를 어떻게 보낼까 | 초기 구현은 Gmail SMTP, 캡차·대기·횟수 제한 병행 | SES 등 전용 발송 서비스도 한도·반송·평판 관리 필요 |
| 번호와 링크 중 무엇을 쓸까 | 화면에서 번호를 입력해 확인 | 링크도 가능하나 둘 다 같은 이메일 접근 증거이며 이중 인증은 아님 |
| Redis TTL 대신 DB 기한을 둔 이유 | 인증 완료·소비·회원 생성을 같은 DB에서 관리하고 트랜잭션으로 묶음 | Redis도 적절한 선택. 다만 DB 회원 생성과 별도 저장소 소비의 실패 처리가 추가됨 |
| 다른 만료 구현은 없을까 | 요청 시 `expires_at` 검사, 만료 행은 별도 정리 | 서명된 만료 토큰도 가능하나 일회 사용·취소에는 상태 저장이 필요 |
| 왜 인증 기록과 제한 기록을 나눴나 | 재발송으로 실패 누계를 초기화하지 않기 위해 | 저장·정리 대상이 늘어나며 경쟁 상황 검증 필요 |
| 이메일 중복을 미리 안내할까 | 가입 시 중복 안내로 사용 흐름을 단순화 | 이메일 가입 여부가 드러나는 절충이 있음 |
| 세션과 JWT 중 무엇을 쓸까 | JWT Access + 무작위 Refresh + 서버 로그인 기록 | 서버 세션도 충분한 대안. 현재는 DB 조회하므로 무상태·조회 제거를 장점으로 내세우지 않음 |
| 토큰 저장 위치 | HttpOnly 쿠키 | localStorage는 JS가 읽을 수 있음. JS 메모리는 새로고침 시 사라짐. 쿠키에는 CSRF 방어 필요 |
| 왜 Access와 Refresh를 나눴나 | 짧은 접근 수명과 서버에서 관리하는 재발급 이력 분리 | 구성과 경쟁 처리가 복잡해짐. 두 기간을 더해 유지 기간으로 계산하지 않음 |
| 이전 토큰 요청이 곧 공격인가 | 네트워크 재시도·동시 요청을 고려해 5초 동안 같은 결과 허용 | IP·User-Agent 일치만으로 정상 사용을 확정할 수 없음. 유예는 고정이며 연장하지 않음 |
| DB에 토큰 원문을 둘까 | HMAC 검증값 저장 | 재시도 응답은 별도 암호문으로 일시 보관. 서버 비밀키까지 유출되는 상황을 모두 해결하지 않음 |
| Google 이메일이 같으면 합칠까 | 명시적으로 인증한 계정 연결만 허용 | 여러 인증 제공자로 확장하면 별도 계정 연결 테이블 검토 |
| 인증 성공인데 회원 저장이 실패하면 | 회원 생성과 인증 소비를 함께 롤백 | 메일 전송은 외부 작업이라 롤백되지 않음 |
| 여러 창에서 일기를 수정하면 | 버전으로 오래된 저장을 거절하고 작성 내용 보존 | 충돌 내용을 합치는 UX는 별도 문제 |
| 반복 설정과 오늘 체크를 합칠까 | 반복 규칙과 날짜별 수행 상태를 분리 | 생성되지 않은 날짜의 과거 제목까지 완전하게 보관하지는 않음 |
| 입력 중 내용을 어떻게 보존할까 | 브라우저의 회원·날짜별 임시 복구와 명시적 서버 초안 저장 구분 | 임의의 30초·30분 자동 서버 저장 정책으로 설명하지 않음 |
| 개인정보를 얼마나 받을까 | 사용하지 않는 생년월일·전화번호 제거, 공개 작성자는 닉네임/익명 | 이름은 실명 인증값이 아님. 기존 동의 버전은 덮어쓰지 않음 |

## 깊이 설명할 핵심 세 가지

**인증 완료와 사용 완료는 다르다.** 번호를 맞혔다는 기록만으로 여러 회원 생성 요청을 허용하면 안 된다. 최종 가입에서 같은 기록을 잠그고 다시 검사하며 회원 생성과 소비를 한 번에 저장한다.

**토큰의 만료와 로그인 종료는 다르다.** 7일이 남아 있어도 로그아웃 시 서버 로그인 기록을 종료한다. 반면 이전 Refresh Token 재사용 탐지 시 현재 정책은 재발급만 차단한다. 두 상황을 섞어 설명하지 않는다.

**화면 검증·API 검증·DB 제약은 역할이 다르다.** 화면은 빠른 안내, API는 권한과 업무 규칙, DB는 경쟁 중에도 유지해야 할 관계·중복 규칙을 담당한다. 한 계층만으로 모든 문제를 해결했다고 보지 않는다.

## 남은 개선

메일 발송 작업과 재시도를 관리하는 구조, Gmail에서 전용 발송 서비스로 전환할 기준, PostgreSQL에서 로그인·재발급·일기 경쟁 검증, 운영 부하에 맞는 해시 비용, 정리 예약 실행 감시, DB 최소 권한과 연결 보안 보강이 남아 있다. 보존 기간·유예·로그인 기간은 현재 정책이며 보편적인 정답은 아니다.
