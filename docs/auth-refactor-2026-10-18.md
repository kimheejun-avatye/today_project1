# 인증 구조 수정 내역 — 2026-10-18

대상: 하루 일기 / `kimheejun-avatye/today_project1`.
이 문서는 이번 작업에서 무엇을 왜 바꿨는지 설명하기 위한 코드 리뷰 안내다.

## 1. 변경 목적

기존에는 JWT를 사용하면서 일반 요청마다 로그인 세션 기록도 조회했다. 로그아웃 직후 복사된 Access까지 차단할 수 있지만, 세션 상태와 Refresh 이력을 함께 관리해야 했다.

이번에는 로그인 세션 테이블을 제거하고 일반 요청의 인증은 JWT 검증으로 처리하기로 했다. 대신 로그아웃 전 복사한 Access의 남은 유효기간을 최대 5분까지 허용한다. 기능에 필요한 회원·일기 DB 조회까지 제거한 것은 아니다.

## 2. 변경 전후

| 항목 | 이전 | 변경 후 |
|---|---|---|
| Access 수명 | 최대 15분 | 최대 5분 |
| 전체 로그인 수명 | 최초 로그인부터 7일 | 최초 로그인부터 4시간 |
| 일반 요청 | JWT + 로그인 세션 조회 | JWT 검증 + 필요한 회원 조회 |
| 로그인 상태 저장 | login_sessions + refresh_tokens | refresh_tokens만 사용 |
| Refresh 교체 | 새 행과 이전 토큰 연결 | 같은 행의 digest 갱신 |
| 로그아웃 | 세션 종료 표시 | 해당 Refresh 행 삭제 |
| 이전 토큰 유예 | 5초 동안 같은 응답 복구 | 제거 |
| 이전 토큰 재사용 탐지 | 이력으로 재발급 권한 차단 | 이전 토큰 거절, 이력 기반 추적 없음 |

4시간은 고정 기한이다. 재발급할 때 연장하지 않는다. Access 만료는 `현재 시각 + 5분`과 `최초 로그인 + 4시간` 중 이른 시각이다.

## 3. DB에서 바꾼 것

실제 연결된 PostgreSQL의 `login_sessions`를 삭제했다. `refresh_tokens`는 아래 네 컬럼으로 교체했다.

| 컬럼 | 역할 | 제약 |
|---|---|---|
| id | 현재 토큰 기록 식별자 | 기본키 |
| member_id | 회원 연결 | 외래키, 필수, 고유 |
| digest | Refresh 전체 문자열의 HMAC-SHA256 검증값 | 필수, 고유 |
| expires_at | 최초 로그인부터 4시간 만료 시각 | 필수, 인덱스 |

회원당 현재 Refresh 한 건을 유지한다. 새 로그인 시 이전 행을 삭제한다. 기존의 session_id, previous_id, rotated_at, retry_until, retry_payload는 제거했다.

변경 전 로컬 비공개 백업을 만들고 한 트랜잭션에서 변경했다. 인증 두 테이블 외 모든 행을 변경 전후 비교했다. 회원 3명, 일기 3건, 반복 할 일 3건, 댓글 1건, 날짜별 할 일 4건의 내용이 보존됐다. 기존 로그인은 초기화되어 재로그인이 필요하다.

## 4. 코드 리뷰 순서

1. [토큰 발급](../backend/app/services/tokens.py): 기존 sessions.py를 대체한다. 회원 잠금 → 기존 Refresh 삭제 → 새 난수 발급 → DB 확정 → 쿠키 설정 순서다.
2. [보안 공통 처리](../backend/app/core/security.py): 5분/4시간 상수, JWT 검증, CSRF와 쿠키 설정. 일반 요청에서 로그인 세션 조회를 제거했다.
3. [재발급·로그아웃](../backend/app/services/refresh.py): ID는 유지하고 해시만 교체한다. 행 잠금과 기존 해시 조건부 갱신으로 중복 회전을 막는다.
4. [인증 API](../backend/app/api/routes/auth.py): Refresh 기반 로그아웃과 비밀번호 재설정 후 Refresh 삭제. Google 로그인도 같은 발급 함수를 사용한다.
5. [프론트 통신](../frontend/src/shared/api/client.ts): Access 만료 시 재발급 후 원래 요청을 한 번만 재시도한다. 같은 탭은 Promise를 공유하고 Web Locks 지원 환경은 여러 탭도 조율한다.
6. [화면 시작점](../frontend/src/main.ts): 만료 시각을 주기적으로 확인하고 화면 복귀 때도 재검사한다. 기존 재로그인 안내와 작성 내용 보존 기능을 사용한다.
7. [데이터 정리](../backend/app/maintenance.py): 만료 Refresh를 삭제한다. 정리 작업 실행 전이라도 만료 토큰은 사용할 수 없다.
8. [명시적 DB 변경 스크립트](../backend/scripts/migrate_refresh_only.py): 백업·트랜잭션·비인증 행 보존 검사·재실행 방지를 포함한다. [변경 SQL](../backend/sql/006_refresh_only.sql)과 [정리 함수](../backend/sql/003_auth_retention.sql)를 함께 적용한다.

## 5. 보안과 경쟁 처리에서 유지한 것

- Access·Refresh는 HttpOnly, 운영에서는 Secure 쿠키로 전달한다. SameSite와 Origin 검사도 유지한다.
- 세션의 csrf_digest 대신 서명된 CSRF를 사용한다. 쿠키·헤더 일치, 서명, 종류, 기한, 회원과 기록 ID 연결을 확인한다.
- JWT의 rid는 CSRF 연결용이다. 일반 요청에서 해당 ID로 Refresh를 조회하지 않는다.
- Refresh는 `기록 ID.보안 난수` 형태다. ID만으로 재발급할 수 없고 전체 문자열의 해시가 일치해야 한다.
- 재발급과 로그아웃이 겹쳐 비밀값이 바뀌어도, 서명된 CSRF로 같은 기록을 확인해 삭제한다.
- 이미 만료된 CSRF의 서명을 인정하는 예외는 로그아웃의 기록 삭제에만 적용한다. Access 인증과 재발급은 만료를 허용하지 않는다.
- 비밀번호 재설정과 새 로그인은 이전 Refresh를 삭제한다. 이미 발급한 Access의 즉시 차단은 제공하지 않는다.

## 6. 감수한 제한

- 로그아웃 전에 복사된 Access는 최대 5분 유효할 수 있다.
- Refresh 교체 응답이 유실되면 재로그인이 필요할 수 있다. 5초 유예와 응답 복구는 제거했다.
- 이전 토큰의 이력을 저장하지 않으므로 그 이력에 기반한 최신 토큰 폐기 기능은 없다.
- 브라우저 타이머는 안내용이다. 절전 중 정확한 순간에 화면을 바꾸는 것은 보장하지 않으며, 복귀 시 다시 확인한다. 서버 만료 검사는 별개다.
