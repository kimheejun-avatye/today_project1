# 가입·로그인 인증 정책

정리 기준: 2026-10-18. 이 문서는 현재 정책을 설명한다. 설정 절차는 [운영 안내](operations.md), 대안 비교는 [설계 결정](decisions.md)를 참고한다.

## 이메일 발송과 가입

이메일 인증은 해당 메일함에 접근할 수 있음을 확인한다. 실명·법적 본인 확인을 의미하지 않는다. 서버가 임의의 6자리 코드를 만들고 Gmail SMTP를 통해 보낸다. SMTP는 이메일 전송 규약이며 번호를 생성하는 주체는 우리 서버다.

1. 캡차와 요청 제한을 확인한다.
2. 이메일을 발송하고 인증 기록을 저장한다. 유효기간은 10분이다.
3. 코드 입력 시 검증값을 비교하고 `verified_at`을 기록한다.
4. 최종 가입 시 기록의 대상·목적·기한·확인·미소비 상태 및 요청 비밀값을 다시 검사한다.
5. 인증 기록을 잠근 뒤 다시 검사하고 회원 생성과 `consumed_at` 기록을 같은 트랜잭션으로 저장한다.

마지막 검사는 사용자에게 코드를 다시 입력시키는 것이 아니다. 번호 확인 후 가입 버튼을 누르기까지 기록이 만료되거나 이미 사용됐는지 서버가 확인하는 것이다. 비용이 큰 비밀번호 해시는 잠금 전에 계산하고 잠금 뒤 인증 상태를 재검사한다.

| 제한 | 현재 정책 |
|---|---|
| 같은 이메일·목적 재전송 | 60초 간격 |
| 메일 요청 IP 제한 | 15분 동안 20회 |
| 코드 검증 실패 | 15분 집계에서 5회 실패 제한 |
| 재발송 | 기존 인증 무효화, 별도 실패 누계 유지 |

SMTP 성공 응답은 메일 서버의 접수이며 받은편지함 도착 보장은 아니다. 발송 후 DB 실패 가능성도 남아 있다. Gmail의 실제 한도는 계정 유형과 제공자 정책에 따라 확인해야 한다. Amazon SES 등으로 바꿔도 할당량·발송 속도 제한이 없어진다고 설명하지 않는다.

## 비밀번호와 Google

비밀번호는 `argon2-cffi`의 `PasswordHasher`로 해시한다. 가입·재설정 비밀번호는 12~128자다. 이 값은 바이트 수와 구분한다. 추가 입력 제약은 [요청 모델](../backend/app/schemas/auth.py)과 [보안 코드](../backend/app/core/security.py)를 함께 확인한다. 라이브러리 기본값 사용과 서비스가 부하 측정으로 비용을 조정한 것은 구분한다.

Google 로그인은 서버에서 ID 토큰을 검증하고 대상 클라이언트, 이메일 확인 여부, `sub` 등을 확인한다. Google 식별자는 `members.google_subject`에 고유하게 저장한다. 같은 이메일이라는 이유만으로 기존 계정에 자동 연결하지 않는다. 계정 연결은 로그인 상태·CSRF·이메일 일치·비밀번호·동의를 확인하는 별도 작업이다. 현재는 Google 외 여러 제공자를 관리하는 별도 테이블이 없다.

## 로그인과 토큰

- Access는 HS256 JWT이며 최대 5분. 최초 로그인부터 4시간을 넘지 않는다.
- Refresh는 기록 UUID와 보안 난수의 조합이며 DB에는 전체 문자열의 HMAC-SHA256 검증값만 저장한다.
- `refresh_tokens`는 id, member_id, digest, expires_at 네 컬럼이다. member_id 고유 제약으로 회원당 하나만 유지한다.
- 로그인 세션 테이블은 없다. 일반 요청은 JWT를 검사하고 회원을 조회하며, Refresh 기록을 조회하지 않는다.
- 재발급은 같은 행의 digest만 교체하고 최초 4시간 만료 시각은 유지한다.
- 로그아웃은 해당 Refresh 행을 삭제하고 쿠키를 삭제한다. 새 로그인·비밀번호 재설정도 이전 Refresh를 삭제한다.
- 복사된 Access는 최대 5분간 유효할 수 있다. 즉시 전체 접근 차단이나 엄격한 단일 Access 정책은 제공하지 않는다.

## 재발급 경쟁과 종료

같은 탭은 재발급 Promise를 공유한다. Web Locks 지원 브라우저는 탭 간 재발급·로그아웃도 직렬화하고, 다른 탭이 쿠키를 갱신했다면 다시 재발급하지 않는다. 서버는 행 잠금과 조건부 갱신으로 중복 회전을 차단한다.

이전 토큰 이력과 5초 유예는 제거했다. 응답 유실로 새 Refresh를 받지 못하면 재로그인이 필요할 수 있다. 오래된 토큰은 거절하지만 그 이력으로 최신 토큰까지 폐기하는 탐지는 제공하지 않는다.

로그아웃은 Access 만료와 무관하게 처리한다. 서명된 CSRF의 회원·기록 ID를 확인해, 동시에 Refresh 비밀값이 바뀌어도 같은 기록을 삭제할 수 있다. 기록 ID만으로 재발급은 불가능하다.

화면은 서명된 CSRF에 담긴 종료 시각으로 재로그인 안내를 표시하고 작성 내용을 보존한다. 이 화면 타이머는 보안 판정이 아니며 서버의 JWT/Refresh 만료 검사가 기준이다. 만료된 Refresh는 정리 작업에서 삭제한다.

## 쿠키와 요청 보안

Access·Refresh 쿠키에 `HttpOnly`를 적용해 JavaScript의 직접 읽기를 막는다. 운영에서는 `Secure`로 HTTPS 전송을 요구하고 `SameSite=Lax`를 사용한다. 쿠키는 여전히 브라우저에 저장되며 자동으로 전송된다.

자동 전송되는 로그인 쿠키를 이용해 다른 사이트가 사용자를 대신한 변경 요청을 보내는 문제가 CSRF다. 서버는 변경 요청의 Origin과 CSRF 쿠키·헤더 일치, 서명, 종류, 기한, 로그인별 기록 ID를 확인한다. 일반 요청은 JWT의 기록 ID와, 재발급은 Refresh 기록 ID와 연결한다. 로그아웃에서는 이미 만료된 서명된 CSRF도 해당 기록 삭제에 한해 허용한다. CSRF 쿠키는 화면 코드가 요청에 실어 보낼 수 있도록 읽기 가능하다. HttpOnly만으로 XSS나 로그인 상태에서의 악성 동작을 모두 차단할 수는 없다.

로그인 실패는 이메일·IP 단위로 제한하며 반복 실패 시 대기시간을 늘린다. 실제 제한 조건은 [인증 라우터](../backend/app/api/routes/auth.py)와 [제한 구현](../backend/app/db/controls.py)이 기준이다.
