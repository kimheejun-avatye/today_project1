# DB 설계서

작성 기준: 2026-10-13. 현재 SQLAlchemy 모델과 기존 설계 논의를 정리한 DB 전문 문서다.

## 1. 적용 범위와 문서 관계

전체 시스템은 [전체 구조](architecture.md), 회원가입 정책은 [인증 정책](authentication.md)를 따른다. 이 문서는 저장 구조·관계·제약·트랜잭션·조회·생명주기를 정의한다. 인증 정책은 인증 문서에서 관리하며 실제 구현과 함께 확인한다.

아래 데이터 사전은 [현재 모델](../backend/app/models/)을 기준으로 한다. 후속 제안은 별도 절에 분리한다. 2026-10-13에는 캡차·개인정보 동의 컬럼을 추가하고 임시 PostgreSQL에서 가입 경쟁·롤백·회원 컬럼 추가를 검증했다. 전체 운영 DB 검증 완료와 구분한다.

## 2. DB 선택과 이유

운영 DB는 PostgreSQL을 사용한다. 회원·기록 관계, 중복 금지, 상태 제약과 트랜잭션을 관계형 구조로 표현하고 학습하는 목적에 맞는다. 현재 단일 활성 로그인을 위한 부분 고유 인덱스도 모델에 정의되어 있다.

| 비교 대상 | 얻는 장점 | 이번 판단 |
|---|---|---|
| PostgreSQL | 관계·고유 제약, 트랜잭션, 부분 인덱스 등 데이터 규칙 표현 | 운영 기준 DB로 선택, 서버 운영·백업 부담 수용 |
| MySQL/InnoDB | 현재 CRUD와 관계형 무결성 요구를 충족할 수 있음 | 팀 숙련도·기존 환경이 있으면 대안, 현재 기능만으로 열등하다고 판단하지 않음 |
| SQLite | 별도 DB 서버 없이 로컬 개발 가능 | 이전 원본·백업 및 별도 테스트에 사용. 2026-10-13에는 API의 Supabase PostgreSQL 전환을 확인했으며 SQLite 검사는 PostgreSQL 잠금 검증을 대체하지 않음 |
| MongoDB | 관련 정보를 문서 단위로 묶어 다룰 수 있음 | 이번에는 회원·반복·날짜별 관계와 제약을 관계형으로 표현하기로 함 |

Redis나 별도 인증 저장소는 두지 않는다. 회원 생성과 인증 소비를 같은 DB 트랜잭션으로 묶고 운영 대상을 줄이는 대신, 만료 확인과 데이터 정리가 필요하다.

## 3. 모델링 원칙

- 회원은 변경 가능한 이메일 대신 내부 `members.id`로 연결한다.
- 회원당 날짜별 일기는 하나이며, 일기가 없어도 할 일을 등록할 수 있다.
- 반복 설정과 날짜별 수행 상태는 별도로 저장한다.
- 저장된 날짜별 할 일의 제목은 당시 값을 보관한다. 미생성 날짜의 제목 이력은 현재 구조만으로 보존되지 않는다.
- 인증 성공과 최종 사용 완료를 구분한다. 재전송해도 남용 제한 기록은 별도로 유지한다.
- 외래키는 연결의 유효성을 보장하며 요청자의 접근 권한은 API에서 검사한다.
- 날짜마다 테이블을 만들지 않는다. 하나의 DB 안에 아래 10개 테이블을 둔다.

## 4. 전체 관계

```text
members
 ├─ email_verifications  (가입 전에는 member_id 없음)
 ├─ login_sessions
 │    └─ refresh_tokens ── previous_id로 이전 토큰 참조
 ├─ diaries
 │    └─ comments ── 작성자는 members 참조
 ├─ recurring_tasks
 │    └─ daily_tasks  (반복 설정과 회원을 함께 참조)
 └─ daily_tasks       (일회성 항목은 recurring_task_id 없음)

rate_limits: 이메일·목적·접속 주소 등에 대한 제한 키별 상태
captcha_challenges: 가입 전에도 사용하는 일회 이미지 확인 기록
```

회원과 각 기록은 1:N 관계다. 날짜별 할 일은 반복 설정을 선택적으로 참조한다. `rate_limits`는 회원 가입 전에도 필요하므로 회원 FK가 없는 독립된 제한 상태다. 캘린더와 별도 로그인 제공자 테이블은 현재 두지 않는다.

## 5. 현재 데이터 사전

PK는 기본 키, FK는 외래키다. 아래 ‘필수’는 현재 모델의 NOT NULL 또는 PK를 뜻하며 API 필수 입력과 구분한다. 기본값은 별도 표기가 없으면 SQLAlchemy의 애플리케이션 기본값이며 DB 서버 기본값으로 보장되는 것은 아니다. 시각의 Integer는 Unix 초, 날짜의 String(10)은 `YYYY-MM-DD` 형식이다.

### `members` — 정식 회원

이메일·Google 식별자는 각각 고유하다. 비밀번호 해시 또는 Google 식별자 중 하나는 있어야 한다. 닉네임·동의 기록은 기존 회원 보존을 위해 DB에서는 NULL 허용이며 일반·Google 신규 가입에서는 API가 필수로 검사한다. 닉네임은 고유 제약이 없다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `Integer` | PK; 필수 |
| `email` | `String(254)` | 필수; 고유 |
| `password_hash` | `Text` | NULL 허용 |
| `name` | `String(80)` | 필수 |
| `nickname` | `String(40)` | NULL 허용 |
| `google_subject` | `String(255)` | NULL 허용; 고유 |
| `privacy_consent_version` | `String(60)` | NULL 허용; 안내 버전 |
| `privacy_consented_at` | `Integer` | NULL 허용; 서버 동의 시각 |

### `email_verifications` — 이메일 인증 과정

목적, 대상 이메일, 코드·요청 비밀값 검증값, 만료·확인·소비 시각을 보관한다. 가입 전 member_id는 NULL이다. 코드 원문을 저장하지 않는다. 회원 생성과 consumed_at 갱신을 같은 트랜잭션으로 처리한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `String(36)` | PK; 필수 |
| `member_id` | `참조 PK와 같은 타입` | NULL 허용; ForeignKey('members.id') |
| `email` | `String(254)` | 필수 |
| `purpose` | `String(30)` | 필수 |
| `code_digest` | `String(64)` | 필수 |
| `flow_digest` | `String(64)` | 필수 |
| `expires_at` | `Integer` | 필수 |
| `verified_at` | `Integer` | NULL 허용 |
| `consumed_at` | `Integer` | NULL 허용 |

### `captcha_challenges` — 이미지 캡차 확인

이미지의 숫자와 일회 확인 증거는 각각 HMAC 검증값으로 저장한다. 회원 FK는 없으며 개인정보 프로필로 저장하지 않는다. 정답 확인·소비 시 행 잠금을 사용한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `String(36)` | PK; 필수 |
| `code_digest` | `String(64)` | 필수; ID와 숫자를 함께 검증 |
| `proof_digest` | `String(64)` | NULL 허용; 정답 확인 후 발급 |
| `expires_at` | `Integer` | 필수; 조회 인덱스 |
| `verified_at` | `Integer` | NULL 허용 |
| `consumed_at` | `Integer` | NULL 허용 |
| `attempts` | `Integer` | 필수; 기본값 0 |

### `rate_limits` — 남용 제한

key가 제한 단위를 식별한다. count와 시간 정보를 관리하며 재발송으로 실패 누계가 초기화되지 않도록 인증 요청과 분리한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `key` | `String(300)` | PK; 필수 |
| `count` | `Integer` | 필수; 기본값 0 |
| `started_at` | `Integer` | 필수; 기본값 now |
| `blocked_until` | `Integer` | 필수; 기본값 0 |
| `last_sent_at` | `Integer` | 필수; 기본값 0 |

### `login_sessions` — 서버 로그인 상태

revoked_at IS NULL인 행은 회원당 하나만 허용하는 부분 고유 인덱스가 있다. 만료 여부도 별도 검사해야 한다. refresh_revoked_at은 재발급만 차단하는 상태이며 전체 종료와 구분한다. member_id 조회 인덱스가 있다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `String(36)` | PK; 필수 |
| `member_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('members.id') |
| `expires_at` | `Integer` | 필수 |
| `revoked_at` | `Integer` | NULL 허용 |
| `refresh_revoked_at` | `Integer` | NULL 허용 |
| `csrf_digest` | `String(64)` | 필수 |

### `refresh_tokens` — 재발급 토큰 교체 이력

digest와 previous_id는 각각 고유하다. 최초 previous_id는 NULL이다. session_id 조회 인덱스가 있다. retry_payload는 5초 유예 동안 같은 응답을 반환하기 위한 인증 암호문이다. 무작위 토큰 검증값과 구분하며 유예가 끝난 암호문은 매시간 정리한다. 토큰 행 자체는 로그인 종료·만료 후 24시간까지 유지해 재사용 탐지에 사용한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `String(36)` | PK; 필수 |
| `session_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('login_sessions.id') |
| `digest` | `String(64)` | 필수; 고유 |
| `previous_id` | `참조 PK와 같은 타입` | NULL 허용; 고유; ForeignKey('refresh_tokens.id') |
| `expires_at` | `Integer` | 필수 |
| `rotated_at` | `Integer` | NULL 허용 |
| `retry_until` | `Integer` | NULL 허용 |
| `retry_payload` | `Text` | NULL 허용 |

### `diaries` — 날짜별 일기

UNIQUE(member_id, diary_date), status IN (DRAFT, FINAL), 공유하려면 FINAL이라는 CHECK가 있다. version은 편집 충돌 검사에 사용한다. 같은 행을 초안에서 등록으로 갱신한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `Integer` | PK; 필수 |
| `member_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('members.id') |
| `diary_date` | `String(10)` | 필수 |
| `content` | `Text` | 필수; 기본값 '' |
| `emotion` | `String(40)` | 필수; 기본값 '' |
| `status` | `String(10)` | 필수; 기본값 'DRAFT' |
| `is_shared` | `Boolean` | 필수; 기본값 False |
| `version` | `Integer` | 필수; 기본값 1 |
| `updated_at` | `Integer` | 필수; 기본값 now |

### `recurring_tasks` — 매일 반복 설정

UNIQUE(id, member_id)는 날짜별 항목에서 소유자까지 복합 FK로 연결하기 위한 제약이다. end_date는 마지막 적용일이며 NULL이면 종료 미정이다. 종료일 범위는 현재 API에서 검사하며 DB CHECK는 아직 없다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `Integer` | PK; 필수 |
| `member_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('members.id') |
| `title` | `String(200)` | 필수 |
| `start_date` | `String(10)` | 필수 |
| `end_date` | `String(10)` | NULL 허용 |

### `daily_tasks` — 날짜별 실제 할 일

UNIQUE(recurring_task_id, task_date)로 반복 항목 중복을 막는다. 반복 ID가 NULL인 일회성 항목은 하루 여러 개 가능하다. (recurring_task_id, member_id)가 recurring_tasks(id, member_id)를 참조해 다른 회원의 반복 설정과 연결되는 것을 막는다. member_id 인덱스가 있다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `Integer` | PK; 필수 |
| `member_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('members.id') |
| `recurring_task_id` | `Integer` | NULL 허용 |
| `task_date` | `String(10)` | 필수 |
| `title` | `String(200)` | 필수 |
| `completed` | `Boolean` | 필수; 기본값 False |

### `comments` — 공유 일기의 댓글

diary_id는 ON DELETE CASCADE이므로 일기 삭제 시 댓글도 삭제한다. member_id는 댓글 작성자다. diary_id 조회 인덱스가 있다. 조회·작성 시 공유 여부, 삭제 시 댓글 작성자를 API에서 확인한다.

| 컬럼 | 현재 모델 타입 | NULL·제약·기본값 |
|---|---|---|
| `id` | `Integer` | PK; 필수 |
| `diary_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('diaries.id', ondelete='CASCADE') |
| `member_id` | `참조 PK와 같은 타입` | 필수; ForeignKey('members.id') |
| `content` | `String(2000)` | 필수 |
| `created_at` | `Integer` | 필수; 기본값 now |

## 6. 핵심 트랜잭션과 동시성

| 작업 | 함께 처리할 변경 | 실패·경쟁 시 보장할 것 |
|---|---|---|
| 일반 가입 | 회원 생성 + 인증 기록 소비 | 회원 저장 실패 시 소비도 롤백, 이메일 중복은 고유 제약으로 차단 |
| 새 로그인 | 기존 로그인 종료 + 새 로그인 생성 | 동시에 요청해도 활성 상태 최대 하나 |
| 토큰 교체 | 기존 교체 상태 + 새 토큰 + 유예 응답 | 후속 토큰 분기 방지, 직전 토큰 재시도 결과 일치 |
| 비밀번호 재설정 | 해시 변경 + 인증 소비 + 기존 로그인 차단 | 일부만 성공하는 상태 방지 |
| 일기 저장 | 기존 버전 확인 + 본문·상태·버전 갱신 | 오래된 버전은 409, 최초 생성 경쟁은 고유 제약으로 중복 차단 |
| 반복 항목 체크 | 반복 소유·기간 확인 + 날짜별 행 생성/수정 | 날짜별 중복 없이 원하는 completed 상태 저장 |

실제 PostgreSQL에서 동일 인증 가입의 잠금 대기와 다른 인증의 독립 처리, 서로 다른 인증의 동일 이메일 중복 차단, 회원 저장 실패 시 인증 소비 롤백을 검증했다. 로그인·토큰·일기·반복 체크의 PostgreSQL 경쟁 검증은 아직 남아 있다. 가입 비밀번호 해시는 인증 기록 잠금 전에 계산하고 잠금 후 증거를 재검사한다.

메일 발송은 외부 작업이므로 DB 트랜잭션으로 취소할 수 없다. 발송 성공 후 DB 저장 실패 가능성과 재요청 안내는 [인증 정책](authentication.md)의 한계를 따른다.

## 7. 반복 기록 생성과 이력의 현재 동작

1. 반복 등록 시 반복 설정과 지정한 시작 날짜의 실제 항목을 생성한다.
2. 날짜 조회는 저장된 daily_tasks와 해당 날짜에 적용되는 recurring_tasks를 조합한다.
3. 아직 날짜별 행이 없으면 미완료 항목을 응답에만 추가한다. GET 조회는 DB 행을 생성하지 않는다.
4. 완료 상태 변경 시 날짜별 행이 없으면 생성하고 당시 제목을 저장한다.
5. 반복 중단은 end_date를 지정하며 해당 날짜까지 포함한다.

이 방식은 접속하지 않은 날짜도 현재 반복 설정으로 표시할 수 있지만 모든 과거 제목을 보존하지는 못한다. 현재 반복 제목 편집은 제공하지 않는다. 제목 수정 기능을 추가하려면 적용 기간별 버전 또는 날짜별 생성 정책을 먼저 정한다.

이미 생성된 미래 daily_tasks는 현재 조회에서 별도로 반환되므로 반복 종료일을 앞당겨도 자동 제거되지 않는다. 종료 후 미래 행을 유지·숨김·삭제할지 결정하고 처리해야 한다. 제목 스냅샷만으로 반복 이력 문제가 모두 해결되었다고 보지 않는다.

## 9. 삭제·보관·공유 정책

| 대상 | 현재 구현 또는 정책 | 남은 결정 |
|---|---|---|
| 일기 삭제 | 댓글 CASCADE, 날짜별 할 일은 독립 유지 | 복구·소프트 삭제 필요 여부 |
| 일회성 할 일 | 본인 항목 삭제 | 별도 이력은 현재 없음 |
| 반복 할 일 | 실제 행 삭제 대신 반복 종료 | 이미 생성된 미래 항목 처리 |
| 공유 | 원본 FINAL 일기를 공개, 수정도 반영 | 원본 공개와 복사본 방식 최종 선택 |
| 공유 취소 | 비공개로 변경, 공개 조회·댓글 작성 차단 | 보관 댓글 재공개 정책 |
| 회원 탈퇴 | 기능 미제공 | 연관 기록 삭제·보존·익명화와 FK 동작 |
| 만료 이메일 인증·캡차 | 만료 후 24시간 보관, 매시간 정리 | 실행 결과 점검 |
| 종료·만료 로그인·토큰 | 종료 또는 만료 후 24시간에 토큰 체인을 먼저 지우고 로그인 삭제 | 활성 로그인 토큰 이력 보존 |
| 요청 제한 | 15분 집계·차단·60초 재발송 대기가 모두 끝난 뒤 24시간 | 매시간 정리 |
| 재시도 응답 암호문 | 5초 유예 이후 사용 불가, 매시간 NULL 처리 | 토큰 행과 분리하여 정리 |

만료 데이터가 남아 있다는 이유로 유효하게 취급하지 않는다. 서버 시간으로 만료를 확인한다. 매시간 정리가 정상 실행되면 대상이 된 후 다음 정시에 삭제되며, 잠긴 행은 다음 실행으로 미룬다. 장애가 있으면 실제 삭제가 늦어질 수 있어 실행 결과를 점검한다. 이 정책은 현재 DB 행의 보관 정책이며 기존 백업 파일 삭제를 의미하지 않는다.

## 10. PostgreSQL 적용과 마이그레이션 계획

현재 날짜는 문자열, 시각은 정수로 모델링되어 있다. 기존 ERD의 DATE·TIMESTAMPTZ·UUID 제안과 다르므로 기존 ERD를 현재 물리 스키마로 오해하지 않는다.

후속 제안은 날짜에 DATE, 시각에 TIMESTAMPTZ, 적절한 식별자에 UUID 사용을 검토하는 것이다. 지금 임의로 전환하지 않는다. ‘오늘’의 서비스 시간대도 별도 결정한다.

현재 `create_all`은 초기 생성에 사용하고, `backend/app/db/migrations.py`는 nickname·privacy_consent_version·privacy_consented_at 누락 컬럼을 추가한다. SQLite와 PostgreSQL에서 기존 회원 행을 보존하고 반복 실행할 수 있음을 검사했다. 기존 회원 동의는 NULL로 유지한다. 전체 버전 관리 마이그레이션 체계는 아직 없다.

향후 스키마 변경·운영 배포 시 검증 순서(최초 Supabase 전환은 완료):

1. PostgreSQL 개발 DB를 준비하고 현재 모델로 초기 생성한다.
2. 실제 테이블·제약·인덱스를 모델과 대조한다.
3. 기존 데이터에 NULL·중복·잘못된 날짜가 있는지 검사한다.
4. 스키마 변경 시 버전 관리 마이그레이션과 데이터 변환을 작성한다. 백업 후 복구 가능한지 검증한다.
5. 중복 가입·단일 로그인·토큰 교체·일기 저장·반복 체크 경쟁을 실제 PostgreSQL에서 검사한다.
6. 통과한 환경과 결과를 기록한 뒤 운영 전환한다. 기존 DB를 삭제해 업그레이드하지 않는다.

추가 제약 후보: 반복 종료일 범위, 인증 purpose 허용값, version 양수, 이전 토큰이 같은 로그인에 속한다는 관계. 현재 모델에 모두 구현된 것은 아니며 데이터 정리·API 정책과 함께 적용한다.

## 11. 검증 기준

- 회원 이메일·Google 식별자 중복 차단, 가입 인증 없이 회원 생성 불가.
- 가입 실패 시 인증 소비 롤백, 소비된 기록 재사용 차단.
- 회원당 날짜별 일기 하나, 이메일 변경 후에도 기존 기록의 회원 연결 유지.
- 타인의 반복 설정과 내 날짜별 행 연결 거절.
- 오늘 완료 상태 변경이 내일 완료 상태에 영향을 주지 않음.
- 일기가 없는 미래 날짜에 할 일 저장 가능.
- 단일 활성 로그인, 로그아웃·새 로그인 후 이전 접근 차단.
- 토큰 교체의 동시·재시도 요청에서도 일관된 결과 유지.
- 오래된 일기 버전 저장 거절 및 사용자 작성 내용 보존.
- 일기 삭제 시 댓글 삭제와 독립 할 일 유지.
- PostgreSQL 마이그레이션 후 데이터·제약 보존, 백업 복구 확인.

이 목록은 완료 조건이며 모두 통과했다는 뜻은 아니다. 실행한 가입·인증 검사와 PostgreSQL 검사 범위는 [검증 기록](verification.md)을 참고한다.

따라서 이번 변경은 10개 테이블 사이의 연결을 다시 구성한 것이 아니라 컬럼과 데이터 생명주기를 간소화한 것이다. 관계도는 4절, 현재 컬럼 목록은 5절을 기준으로 한다.

### 적용 기록

- SQLite에서 Supabase PostgreSQL로 회원 2명·일기 2개·반복 설정 2개·날짜별 할 일 3개·댓글 0개를 이전하고 원본과 전체 값을 비교했다. 이는 이전 당시 수치이며 현재 실시간 행 수는 아니다. 기존 SQLite와 백업은 보존했다.
- API의 `DATABASE_URL` 전환과 재시작, 공개 API·프록시 응답을 확인했다. 로그인·인증 임시 기록은 이전하지 않았으므로 다시 로그인해야 한다. 이전 도구와 검증 한계는 [Supabase 연결 진행 상태](operations.md)를 따른다.


- 10개 테이블은 유지한다. 회원·일기·할 일·댓글과 인증/남용 제한은 각각 다른 역할을 가진다.
- `members.birth_date`, `members.phone`, `members.created_at`, `login_sessions.created_at`과 기존 저장값을 제거한다. 동의 시각·댓글 작성 시각·만료/재시도 시각은 유지한다.
- `name`은 내부 회원 정보이며 실명 인증값이 아니다. 공개 작성자는 `nickname`, 기존 NULL 닉네임은 `익명`이다. 본명을 대체 표시하지 않는다.
- 변경된 수집 항목을 개발용 개인정보 안내 `2026-10-13-dev-2`에 반영한다. 기존 동의 버전은 수정하지 않는다.
- `backend/sql/002_remove_unused_profile.sql`: 네 컬럼 삭제. `003_auth_retention.sql`: 제한된 권한의 정리 함수. `004_schedule_auth_retention.sql`: 매시간 정리 예약. 기존 RLS를 유지하며 API 역할에는 함수 실행 권한을 주지 않는다.
- 로컬 기존 DB는 API가 새 코드로 재시작하기 전에 `remove_unused_profile_columns(engine)`을 명시적으로 실행한다. 서버 시작 시에는 파괴적 마이그레이션을 자동 실행하지 않는다.
- 현재 상태: 2026-10-13 Supabase 적용 완료. 삭제 대상 컬럼 잔여 0개, 회원 2명 유지, 10개 테이블 RLS 유지, 매시간 정리 예약 활성화를 확인했다. 정리 함수 최초 실행은 성공했으며 당시 만료 정리 대상은 0건이었다. anon·authenticated 역할의 함수 실행 권한은 없다. 예약에 의한 첫 실행 결과는 아직 확인하지 않았다.

예약 방식은 [Supabase Cron 공식 설치 안내](https://supabase.com/docs/guides/cron/install)를 따른다.

적용 후 로컬 API를 새 코드로 재시작했고 Supabase 연결을 포함한 시작이 성공했다. 실행 중인 OpenAPI의 일반 가입·Google 가입·프로필에서 생년월일·전화번호 필드가 제거된 것을 확인했다.

초기 생성 SQL `001_supabase_schema.sql`은 최초 스키마 이력이다. 최신 상태를 재현할 때는 현재 모델과 후속 `002`~`004` 변경을 함께 확인한다. 초기 SQL만 실행한 상태를 최신 설계로 보지 않는다. 향후 변경도 기존 데이터 백업과 명시적인 마이그레이션으로 관리한다.
